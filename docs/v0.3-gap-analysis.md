# v0.3.0 gap analysis (Reliability & Trust)

Audit of the v0.3.0 plan against the code as of `ca5b7f5` (2026-11-15). Each row says what already
exists, what is missing, and what v0.3.0 does about it. Items that already work are not rebuilt.

## A. Action verification

| Plan item | Already there | Gap | v0.3.0 |
|---|---|---|---|
| Separate dispatch from outcome | `act`/`fill_form` return a `status:` line built from post-action evidence (`session._status`) | The outcome is only text; nothing machine-readable | `Session.last_outcome` (dict: `executed`, `status`, `evidence[]`, `retry_safety`, `recovery[]`), recorded in traces and exposed on `LeanBrowser.last_outcome` |
| Statuses verified / unverified / ambiguous / blocked / timed_out | verified, unverified, timed_out, done | No `blocked` or `ambiguous` | `blocked` = the page rejected it (validation errors, an error alert, HTTP 4xx/5xx) or Lean refused it (confirm or duplicate guard). `ambiguous` = it may have been dispatched but the result can't be confirmed |
| A click alone can't be "verified" | A click with no visible change is `unverified` | **Any** change counted as verified. A signup rejected with a 409 "username taken" page, or a login that lands on "Invalid password", came back `verified (page changed)`. Inline validation errors after submit came back `verified (changes below)` | Error signals (new field errors, `role=alert` error text, HTTP ≥ 400) are checked first and give `blocked`. Submit-like actions need a strong signal: navigation without errors, a success message, a new tab, the form going away, or the caller's `expect`. A UI change alone stays `unverified` |
| Caller-provided postcondition | none | missing | `expect` on `act` and `fill_form`: text that must appear, `url:<part>`, or `gone:<id>`. Checked for up to 3 s |
| Bounded verification | settle is time-boxed (`settle.py`, `PageUnresponsive`) | none | unchanged, plus a bounded `expect` wait |

## B. Safe recovery and duplicate protection

| Plan item | Already there | Gap | v0.3.0 |
|---|---|---|---|
| Re-identify the target with fingerprints | `_resolve_or_recover`: role + name + fingerprint, unambiguous only, **before** anything is executed | none | kept |
| Stop on ambiguity | `ambiguous: ... pick one` error | none | kept; recorded as an outcome |
| Retry-safety classes | `RISKY` regex only marks names as "looks irreversible" | No safe / conditional / unsafe classes | `retry_safety(action, entry)` → `safe`, `conditional` or `unsafe` (risky names, submit buttons, Enter in a form field, `fill_form(submit=…)`) |
| Check partial success before retrying | none (no automatic retries existed) | A failed fill/select/check just errored | Conditional actions that fail check the field state first (already in the wanted state means verified, no retry). A detached target is re-resolved and retried **once**. Unsafe actions are never retried |
| Never blindly repeat unsafe actions | nothing stopped an agent from clicking "Place order" twice | **missing** | Duplicate guard: repeating the same unsafe action on the same page after a `verified`, `ambiguous` or `timed_out` outcome is `blocked` unless `value="confirm"` |
| Navigation during the action | an Obscura click that navigated could surface as a raw "execution context destroyed" error | the action was reported as failed although it happened | treated as dispatched; verification decides the outcome |

## C. Dry-run

Not present. Added: `dry_run=true` on `act` and `fill_form`. It returns JSON with `executed: false`, the
resolved target and context, risk, retry safety and whether confirmation would be needed. It returns
before the dialog policy sync and before `_perform`, so nothing is dispatched. Tests check this with a page
that counts every event and with server-side state.

## D. Traces

| Plan item | Already there | Gap | v0.3.0 |
|---|---|---|---|
| Run / step ids, time, engine, URL, result | `trace.py` (run id, seq, ts, ms, engine, url, status, result) | no outcome evidence, recovery, error category; URL query not redacted | adds `outcome`, `category`; sensitive query parameters (token, code, key, session, signature…) are masked in `url` and `open` args |
| Redaction | password-type fields masked | card / CVV / OTP / token-like fields were stored | fields whose name or autocomplete looks like a card number, CVV, OTP, PIN, token, secret or SSN are masked too |

| Storage, retention, disable | opt-in, 700/600 perms, `trace delete` | retention not documented | documented in SECURITY.md |

## Release hygiene

- Tool count, diagram, spec and roadmap now agree on 7 tools.
- Supported platform: **macOS arm64 only** at v0.3.0. Linux (x86_64, arm64) was added in v0.4.0. No Windows claim.
- Install docs: the repo is private and the package is not on PyPI yet. The README says so.

## Known limitations (carried into README)

- Verification is heuristic. Success and error words are English-only, and a site that shows neither
  stays `unverified`. Pass `expect` when it matters.
- The duplicate guard is per session and per page; it can't know about side effects from another session.
- Dry-run resolves the target from a fresh snapshot, but the page can change before you execute.
- Benchmark sample was small at v0.3.0 (23 tasks); v0.4.0 has 100 fixture tasks; see `docs/benchmark.md`.
- External developer testing of the release candidate is still open.
